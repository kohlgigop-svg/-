# 质检人员质量评估工具

面向数据标注项目的**质检质量评估工具**：输入总体样本量、抽样量与混淆矩阵，自动输出指标点估计、置信区间、召回率警戒线、各指标观察线，并调用大模型生成根因分析与动作建议。

纯前端静态页面，无需后端。数据保存在浏览器本机（localStorage），可导出备份。

**在线地址**：https://kohlgigop-svg.github.io/-/

---

## 一、设计立场（先读这一节）

本工具的目标是**让质量问题显形**，不是评价质检人员。

指标体系回答的是「哪里可能有问题、根因在哪、该做什么」，**不回答「这个人行不行」**。理由有三条，均为可核算的事实：

1. **标准自身有噪声** — 金标准若来自二审，二审的一致率就构成指标天花板。尺子会抖，量不出人的高矮。
2. **任务构成不同则不可横比** — 专判难例与专判简单批的人天然不同分。横向绝对比较等于惩罚承担难例的人。
3. **样本量支撑不住** — 当实际应驳回样本只有 10 条时，召回率的 95% 置信区间宽度可达 **45 个百分点**。用这样的估计给人定性，不是严格，是不严谨。

因此工具内置三条禁令，并写入 AI 提示词的硬性纪律：

- 不许用本指标单独评价个人能力或排名
- 不许在小样本（区间无法收窄）时作任何评价
- 不许把本指标与个人奖惩直接挂钩

> 指标与个人奖惩直接挂钩会立刻诱发指标操纵：压低驳回量即可让精确率好看，同时把风险全部转移给下游。这不是道德问题，是激励设计问题。

| 数据管理 | 项目新建/重命名/删除、按项目或全量导入导出（JSON） |

## 三、计算方法

### 3.1 方向约定

**正例 = 驳回（坏数据）**，负例 = 通过（好数据）。换方向会使召回率与精确率的含义互换。

### 3.2 指标

| 指标 | 公式 | 分母 | 管什么 |
|---|---|---|---|
| 准确率 Acc | (TP+TN)/N | 抽样总数 | 整体协调性；π 偏离均衡时被稀释，**不作主指标** |
| 精确率 P | TP/(TP+FP) | 质检驳回数 | 驳得准不准（**会被 π 稀释**） |
| 召回率 R | TP/(TP+FN) | 实际应驳回数 | 漏没漏（关联不可逆风险） |
| 特异度 Spec | TN/(TN+FP) | 实际合格数 | 冤没冤（**衡量误判只能用这个，不能用 P 代替**） |
| Fβ | (1+β²)·P·R / (β²·P + R) | — | P、R 的加权调和平均，权重比 = **β²** |

**β 的权重关系**：β=2 表示召回率权重是精确率的 **4 倍**（β²），不是 2 倍。

**精确率被 π 稀释的实测值**（固定特异度 99%、召回率 90%）：

| 实际错误率 π | 1% | 5% | 20% | 50% |
|---|---|---|---|---|
| 精确率 P | **47.6%** | 82.6% | 95.7% | 98.9% |

同一个质检员、同样的判定能力，P 随 π 从 47.6% 变到 98.9%。**解读 P 必须同时报 π。**

### 3.3 置信区间

**比例型指标用 Wilson 区间**，不用 Wald。Wald 在 n=100、k=0 时给出 `[0, 0]`，等于宣称漏判率精确为 0；Wilson 给出 `[0, 3.7%]`，才反映真实不确定性。

**F 族指标用参数 Bootstrap**。F1 是 P 与 R 的非线性组合且二者由同一个 TP 决定（负相关），分别求区间再代入会丢掉相关性。Bootstrap 使用固定种子，同一份数据每次得到完全一致的区间，保证可复核。

**n 是各指标自己的分母**，不是抽样总量。同一个抽样集合里 P 与 R 的 n 可能相差一个数量级——这就是「P 不稳」与「R 不稳」是两个不同的病。

### 3.4 警戒线（只对召回率设置）

1. 基线 **B** = 前三次评估的实际驳回率中的最高值（不足三次取全部；无历史则取本次）
2. 容忍率 **T** = 1 − 需求方要求的验收准确率
3. 召回率下限 **R_min** = 1 − T/B；若 R_min ≤ 0（即 B ≤ T），退化为历史最差召回率
4. 可容忍漏判条数 = max(1, 实际应驳回数 × (1 − R_min))

**闭环验证**（单元测试覆盖）：按 R_min 恰好执行时，回代准确率恰好等于验收要求。例：π=8%、验收 95% → T=5% → R_min=37.5% → 可容忍漏判 50 条（分母 80 条）。

判定用**置信区间下限**：下限 ≥ R_min 判为达标；区间跨越 R_min 判为不确定；区间上限低于 R_min 判为确证问题。

> **为什么只给召回率设绝对警戒线**：漏判通常不可逆（坏数据流向模型训练或下游决策）；精确率属返修成本，只在效率维度作相对比较。

### 3.5 观察线

各指标取前 k 次统计的中位数（k 默认 3，可调）。不足 k 次取现有全部值的中位数并标注稳健性有限。**连续两次低于观察线**才提示纳入观察，单次低于不作结论。

### 3.6 分层抽样（⚠️ 非等概率时**必须**填写）

**分层依据必须是「质检判定」**——分层要在拿到金标准之前完成，而"实际应驳回"需要先有金标准，
无法用来分层。因此：

| 层 | 含义 | 抽样数应等于 |
|---|---|---|
| 驳回层 | 质检判为驳回的数据 | `TP + FP` |
| 通过层 | 质检判为通过的数据 | `FN + TN` |

工具会校验这个对应关系，对不上就**停用加权并告警**（用错误权重加权比不加权更危险）。

#### 各层抽样比相同时（等概率分层）：填与不填结果完全一致

P、R、F1 等都是比值，等权重下 `w` 在分子分母中约掉。此时填写只用于展示有效样本量。

#### 各层抽样比不同时（过采样）：**必须填**，否则结论是错的

蒙特卡洛实测（总体真值已知，抽取非等概率分层样本反复模拟）：

「对驳回层过采样 10 倍」（驳回层抽 10%、通过层抽 1%）：

| 指标 | 总体真值 | 样本内口径会显示 | **偏差** | 加权口径 |
|---|---|---|---|---|
| 召回率 | 88.89% | **98.77%** | **+9.88pp** | 88.99% |
| 特异度 | 97.80% | **81.66%** | **−16.14pp** | 97.80% |
| 准确率 | 97.00% | 88.95% | −8.05pp | 97.00% |
| **实际应驳回率 π** | 9.00% | **42.63%** | **+33.63pp** | 9.00% |
| 质检驳回率 τ | 10.00% | 52.63% | +42.63pp | 10.00% |
| 精确率 P | 80.00% | 80.01% | ±0.01pp | 80.01% |

极端情形（驳回层全取）下，特异度偏差达 **−77.98pp**、τ 偏差 **+85.24pp**。

> **精确率 P 与 NPV 不受影响**——它们完全落在单一层内部，权重被约掉。
> 其余指标全部有偏，且 **π 错了 → 警戒线基线 B 与 R_min 全错 → 整个判定失效**。

**置信区间同样失真**：模拟中朴素 Wilson 区间对召回率的覆盖率是 **0.0%**（一次都没覆盖真值），
分层校正后为 **94.9%**（理论值 95%）。

#### 工具如何处理

填写分层且判定为非等概率时，工具自动：

1. 按入样概率倒数加权，把四格计数还原到总体，**以加权值为主口径**
2. 用设计方差（delta 法）＋有限总体校正 `(1−f)` 重算置信区间
3. 在分层设计下重做 Bootstrap（`Bin(n_eff, p)/n_eff`，`n_eff = n/(1−f)`），得到 F 族区间
4. 结果区标注「**加权后总体估计**」，并给出召回率有效样本量与设计效应
5. 诊断卡**说明两种口径差了多少**，提示不要混用
6. **警戒线改用加权 π**——否则基线 B 被严重高估
7. 记录落盘时保存口径标记；历史中混有样本内口径时会告警"观察线不可比"

**τ 的区间宽度为零**：`τ = N₁/N` 是已知的总体比例（层总体数由抽样方案决定），不是估计量。

有效样本量口径：

```
n_eff(经典) = (Σw)² / Σw²            w = 1/入样概率
各指标另有设计方差反解的有效样本量    n_eff = v(1−v)/Var(v̂)
```

> **口径不可混用**：加权后是"总体估计"，样本内是"这批抽样里的表现"，两者回答不同问题。
> 报告时须标明口径；历史观察线要求各周期口径与抽样比一致，否则不可比。
> 相关测试见 `test/stratified.test.js`（64 项，含蒙特卡洛无偏性与覆盖率验证）。

## 四、部署配置（管理员一次配置，全员打开即用）

改 `config.js` 一个文件，重新发布即可。成员打开页面时这些值会自动填好，**不需要任何人再输入**。

| 字段 | 能否写死 | 说明 |
|---|---|---|
| `cloudUrl` | ✅ 能 | Supabase 项目地址，公开信息 |
| `cloudKey` | ✅ 能 | Supabase **anon key**，设计上就是给前端的公开密钥；真正的保护来自数据库行级权限（已实测：拿它直连数据表返回 403） |
| `cloudCode` | ⚠️ 可以但不建议 | 会写进公开仓库，等于公开访问码。建议换成自己的访问码并改用配置串分发 |
| `aiKey` | ❌ **绝对不要** | 这是你的钱。写进公开网页＝任何人 F12 即可抄走刷额度，且有机器人专门扫描 GitHub 上的密钥 |

### 锁定机制

`config.js` 里 `lockDeployment: true` 时，**只有凭据与共享配置会被锁定**：

| 锁定（成员改不了） | 不锁定（成员可在设置里改） |
|---|---|
| `cloudUrl` / `cloudKey` / `cloudCode` / `cloudMode` | `bootstrapB`（Bootstrap 次数） |
| `aiProxyUrl` / `aiBase` / `aiModel` | `alpha`（置信水平） |
| `apiKey`（启用代理时自动锁定） | `obsWindow`（观察线窗口） |
| | `acceptAccuracy` / `maxTokens` |

> **重要**：配置里的计算参数（`bootstrapB`、`alpha`、`obsWindow`、`acceptAccuracy`、`maxTokens`）
> 只作为**默认值**——成员未修改时采用它，改过之后以成员保存的为准。
>
> 判定的唯一依据是 `isLocked()`：**凡界面允许编辑的字段，保存后一定能读回来**；
> 凡界面锁定的字段，一定以部署配置为准。这两者口径必须一致，
> 否则会出现「看起来能改、改了没用」的假可编辑（曾真实发生过）。
> 相关回归测试见 `test/settings.test.js`（36 项）。

### 界面不显示任何凭据

`config.js` 里 `lockDeployment: true` 时：

- **设置界面不显示、也不允许修改任何凭据**：云端 URL、anon key、访问码、AI 代理地址、API Key 全部从界面移除
- 界面只保留非凭据项：同步方式、模型选择、Bootstrap 次数、置信水平、max_tokens
- 另有一个「部署信息」区，**只显示可安全公开的内容**（项目 ref、各项是否已配置），不含任何明文
- 成员无法在界面上改动凭据，因此不会出现「某人误改一个字段导致全员不可用」

> 设计理由：凭据出现在页面 DOM 里本身就是暴露面（浏览器扩展、截图、分享屏幕都可能带出），
> 而且在公开仓库部署的场景下，界面显示等于对外公布。现在凭据只存在于 `config.js`（部署方掌握）
> 与服务端环境变量中。

## 五、使用方式

1. 打开页面 → **新建项目**（项目名用于分组保存历史）
2. 填入评估周期、总体样本量、抽样量、混淆矩阵
3. 点 **计算** → 查看指标矩阵、警戒线推导、预判诊断
4. 点 **保存为记录** → 历史数据自动用于下一次的警戒线与观察线
5. （可选）在 **设置** 中填入 API Key → 点 **生成分析** 获得 AI 根因分析与动作建议

### API Key 说明

工具为纯前端页面，**API Key 保存在你本机浏览器的 localStorage**，不写入代码、不上传任何服务器。仓库源码中不含任何 Key。

首次使用需自行填入（设置 → API Key → 填 `sk-...` → 测试连接）。

> 若要多人共用且不希望各自填 Key，需改用服务端代理方式（如 Cloudflare Worker），不要在公开仓库中嵌入 Key。

## 八、边界与不适用场景

- 适用于**二分类**（通过/驳回）且有金标准的场景
- **不适用多分类**质检（如通过/驳回/返修），需扩展为宏平均或微平均
- **不适用无金标准**场景，此时应改用一致性指标（Cohen's κ、Krippendorff's α）
- 分母为 0 的指标一律显示「不可计算」，**不以 0 冒充**
- 准确率在分层抽样改变类别构成时不代表总体
